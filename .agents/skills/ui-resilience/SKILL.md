# 界面极端数据检查

来源：Emil Kowalski 的 break-ui（MIT，见文末），按 Avalonia 桌面应用改写。目标是用真实可能的数据找出版面问题，不用无意义的长字符串证明界面脆弱。

## 何时加载

- 新增页面、卡片、列表、状态行或配置项之后。
- 用户要求压测、找边界情况、检查长文本或空状态。
- 审阅依赖“演示数据刚刚好”的布局。

## 硬规则

1. 默认只检查和报告，不改代码；修复要用户明确指定范围。
2. 最坏值必须是真实用户可能产生的：真实姓名、真实路径、真实错误日志、真实游戏窗口标题；不用几百个重复字符这类无意义数据。
3. 不碰用户配置、真实任务状态和游戏窗口；在开发构建、临时测试数据或设计态 ViewModel 上进行。
4. 不为测试新增生产开关或长期存在的假数据；临时注入结束后移除。
5. 每个结论给出位置和触发条件；没验证的写“未验证”。

## 步骤

### 1 盘点值

列出界面会显示的值、来源和上限：配置文本、路径、窗口标题、任务名、错误消息、日志、计数、时间、列表长度。找不到上限的标“无界”。

### 2 准备最坏数据

按 [worst-case-data.md](references/worst-case-data.md) 取值，同时覆盖：

- 空：零条目、未选择游戏窗口、未加载配置。
- 单条：一条记录，所有计数为 1。
- 大量：列表到真实上限（日志可到数百行；窗口、卡包数量按实际）。
- 超长：中文长名称、英文长名称、无空格长串（路径、URL、标识符）、中英混合。

### 3 在开发表面渲染

优先用现有设计态 ViewModel、临时测试数据或 Avalonia 设计时数据；不改生产数据源。运行中无法切换时做最小限度的临时注入，结束前移除。

### 4 检查

在最小窗口尺寸（`MainWindow` 1040×700，编辑器窗口各自的 `MinWidth`/`MinHeight`）、100%/150%/200% 缩放、暗色主题下各看一次。有截图能力时同时留存对照。

### 5 报告

按下文格式报告并停下，等用户决定修哪些。

## 失败签名

| 现象 | 常见原因 | 修改 |
|---|---|---|
| 文本溢出容器或被裁掉 | `TextBlock` 没有 `TextWrapping`/`TextTrimming`，或放在不可收缩的列里 | 换行或截断，列用 `*` 并允许收缩 |
| 右侧操作按钮被挤出或裁掉 | 中间内容占满，操作列不是 `Auto` | 中间列可收缩，操作按钮保持最小宽度 |
| 徽章、标签折成两行 | 没有截断，宽度不足 | `TextTrimming` 加 `ToolTip.Tip` 全值 |
| 图标或头像被压扁 | 图标列用了 `*` 或 `Image.Stretch` 不对 | 固定尺寸列，正确 `Stretch` |
| 数字更新时整行跳动 | 比例数字、对齐不稳 | 右对齐或等宽呈现，固定列宽 |
| 长路径把整行撑开 | 没有 `PathSegmentEllipsis` | 用现有路径截断模式加完整值 `ToolTip` |
| 错误信息一行截断且看不到全貌 | 只设了单行 `TextTrimming` | 改成 `TextWrapping="Wrap"` 或给完整入口 |
| 空列表留下空白区域 | 没有空状态 | 加说明文字和“刷新/选择”入口 |
| 200% 缩放后按钮文字裁切 | 固定高度或固定宽度 | 高度从内容来，宽度用 `MinWidth` |
| 日志行高不一、横向溢出 | 混用字体或换行策略 | 固定字号与行高，统一换行或横向滚动 |

## 截断、换行与夹断

- 需要完整识别的名称、标题：换行，最多两行。
- 次要元数据：末尾截断，配完整值 `ToolTip`。
- 路径、文件名、哈希：`PathSegmentEllipsis` 或中间截断。
- 多行预览：`MaxLines` 加 `TextTrimming`。
- 数字、金额、日期、计数：不截断，给足空间。
- 错误与日志：换行或可滚动，不截断。

项目已有做法可直接引用：`MainWindow.axaml` 的配置目录用 `PathSegmentEllipsis` 加 `ToolTip.Tip`，窗口标题用 `CharacterEllipsis`；`ThemeWeightEditorWindow.axaml` 的卡包名用 `Wrap` 加 `CharacterEllipsis` 加 `ToolTip.Tip`。

## 输出格式

### 坏在哪里

一行一个，按严重度排序：**坏**（内容不可读、操作不可达、数据显示错误）、**难看**（能读但明显不对）、**脆弱**（现在正常，一步就坏）。

| # | 严重度 | 字段 | 最坏值 | 现象 | 修改 |
|---|---|---|---|---|---|

每个修改写清文件和控件。

### 需要你决定

有多种正确做法的地方，一行一个，给建议和理由，例如“日志换行还是横向滚动”。

### 没问题的地方

列出已经扛住的最坏情况，说明测试真实覆盖了什么。

结尾说明数据是怎么注入的、检查了哪些尺寸与缩放，以及“指定 fix all 或 fix 1、3 后我再改”。
