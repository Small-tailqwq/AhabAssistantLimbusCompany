# AALC Issue 与日志分析

证据优先。不要假设报告来自 upstream、downstream、canary、某个特定采集后端或当前 `main`；这些事实要从 issue 元数据、配置、日志或发布标识中确认。

## 保护证据

把 `issues/`、日志、截图、提取的配置、分析报告与附件视为用户资产。只做窄读，绝不在原位置删除、移动、覆盖或脱敏。派生报告只写入既定的分析位置。

不暴露日志或配置中发现的凭据、token、cookie 或私有值。在摘要与公开评论中一律脱敏。

## 按证据类型选工具

- 先从 issue 元数据与已有的确定性报告入手。
- 大日志：用 `.opencode/tools/log_analyzer.py`，不要直接打印整个文件。
- 镜像特有证据：用 `.opencode/tools/mirror_analyzer.py`。
- 截图或模板匹配类主张：加载 `replay-matching`，重放命令与管线 reference 归它所有。
- `.opencode/tools/match_viewer.py` 仅在确定性重放之后仍有视觉问题未决时使用。

与截图或模板无关的 issue 不要加载匹配相关 reference。

## 阶段 1：盘点证据

记录已有与缺失的证据来源：

| 事实 | 证据规则 |
|---|---|
| 仓库/通道 | 只能从明确的版本、构建、remote 或功能证据推断 |
| 运行版本 | 按相关运行/会话分别确定；后追加的运行不得覆盖更早事件的版本 |
| 运行模式 | 提取能解释该症状的采集/输入/模拟器/主题/语言设置 |
| 功能路径 | 根据标记与调用点识别实际任务与阶段 |
| 用户症状 | 保留用户原话，再映射到可观察事件 |
| 时间线 | 按时间戳、重启与独立执行分段 |
| 配置 | 只检查能解释症状的键 |

issue 正文、评论、配置与日志相互矛盾时，明确指出矛盾并降低置信度。

## 阶段 2：检查配置与版本

追踪代码前先问：

- 某个相关配置值能否直接解释该行为？
- 事件是否发生在已验证修复之前的版本上？
- 该版本或通道上的相关代码路径是否不同？
- 故障是否由模拟器、窗口、采集或外部运行状态导致？

对照产出证据的发布或 tag 进行比较。不要拿当前 `main` 的代码去诊断旧日志。

## 阶段 3：窄读日志

1. 读一小段开头：启动、版本与模式。
2. 读相关结尾：失败、停止、恢复或最终循环。
3. 搜索精确时间戳、资源键、文件/行标记、异常与阶段标记。
4. 大日志或重复日志用分析器。
5. 只在报告锚点附近回到原始日志。

```powershell
uv run python .opencode/tools/log_analyzer.py <log_path>
```

只引用支撑结论所需的最少行。绝不从一个会话推广到所有追加会话。

## 阶段 4：仅在相关时重放匹配

issue 含截图或依赖模板匹配时加载 `replay-matching`，并走项目完整匹配管线；不要用裸 `cv2.matchTemplate()` 替代。

## 阶段 5：证据指向代码后再追踪

1. 把日志标记映射到精确的源码版本。
2. 读最小的相关调用链与直接调用方。
3. 检查实际 API 签名与邻近模式。
4. 找出修复前必然失败的回归验证基准。
5. 提出最小的行为保持改动。

除非用户的请求包含实现，否则不实现修复。

## 证据模式

| 模式 | 可能方向 |
|---|---|
| 起止标记几乎同时出现 | 配置跳过或前置条件未满足 |
| 重复出现相同的文件/行/资源标记 | 退出条件被卡死或状态检测问题 |
| 上下文资源匹配但动作资源不匹配 | UI/主题/语言/分辨率/覆盖层漂移 |
| 超时后反复重启 | 窗口、游戏、模拟器或采集不稳定 |
| IPC 断连加 traceback | 运行时故障；检查既定恢复契约 |
| 事件版本早于已验证发布的修复 | 先建议升级，再谈新代码 |

这些是假设，不是结论。每条诊断都要落到具体证据上。

## 输出

写最终诊断前，先读 [references/report.md](references/report.md) 了解要求的报告结构。

公开 issue 评论引用源码行时使用精确的 GitHub blob 链接，避免泄露本地路径或私有日志值。
