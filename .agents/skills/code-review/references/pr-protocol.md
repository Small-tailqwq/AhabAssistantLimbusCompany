# 提交、分支、PR 与复审协议

用于多轮 PR 协调或需要跨审阅者追踪的贡献。简单提交、分支和局部复审按 SKILL.md 就地完成，不强制台账。报告模板只保留适用字段。

## 复审的额外证据

收集先前已审阅 SHA、当前 SHA、自先前审阅以来的 delta、完整当前 diff、稳定的发现台账与先前决定。

## 发现台账

在整个审阅生命周期（本地与远端）维护单一台账。

- 分配稳定的 finding ID（`RV-01`、`RV-02`、…）并在每次更新中保留。
- 逐项记录为已修复、仍存在、已被取代、有争议或被拒绝，并附证据。
- 审阅者的原始候选（`NEW-GEN-xx`、`NEW-AUTO-xx`、`NEW-I18N-xx`）只有经协调者核实后才获得稳定台账 ID。
- 不把未改动的旧文本重复当作新发现；没有新证据不重开已定案项——改其既有状态即可。

## 复审步骤

1. 核实哪些先前项已修复、仍存在、被取代、有争议或被拒绝。
2. 审阅 delta 中修复引入的回归。
3. 审阅 delta 影响的上下文，检查交互效应。复用台账中仍有效的完整 diff 覆盖；base、范围或关键依赖变化使先前结论失效时，补读受影响部分。
4. 要求每个真正的新发现标明其变更或直接受影响的触发路径。
5. 把结果绑定到当前 head SHA。

新发现只有在它由被改行、新受影响行为或新获证据的交互引起时才合格。diff 未新调用、修改或依赖的既有路径不构成合格阻断项。

冲突解决、维护者编辑、rebase 或任何推送的改动已审阅代码的修复之后，必须复审。

## 范围决策

提议修正会放宽超时/重试语义、生命周期归属、公开 API、依赖、配置或显式非目标时，先归类为范围决策，再请实现者改代码。审阅者严重度本身不授权范围扩张。

## 裁决矩阵

| 最高剩余结果 | 裁决 |
|---|---|
| 已确认 Critical 或 High 缺陷 | **Block** |
| 已确认 Medium 生产风险，或成片 Medium 缺陷 | **Warning** |
| 只有 Low/Suggestion 项或非阻断验证缺口 | **Approve with comments** |
| 无待办发现且验证与该风险相称 | **Approve** |

验证明显不完整时，不使用裸 **Approve**。

## 完整报告

```markdown
## 审阅概览
- 目标与 base/head：
- 意图与风险面：
- 实际调度：
- 已读上下文：
- 已执行验证：

## 发现
- [RV-01] [Critical/High/Medium/Low/Suggestion] `文件:行` [领域] — 触发条件、影响、证据和修复方向。

## 复审状态
- [RV-01] 已修复 / 仍存在 / 新增 / 不再适用：

## 指引保鲜
- 无需更新，或应更新的常驻规则 / skill / 检查：

## 验证缺口与假设
- 只列影响结论的内容。

**裁决：Block / Warning / Approve with comments / Approve**
```

无发现时明确说明，仍要报告有意义的验证缺口与已审阅 head SHA。
