# 游戏流程证据

用于修改游戏步骤、分支顺序、重试和任务入口。这里帮助定位事实，不代替游戏实测，也不要求重建整个游戏的状态机。

## 一条完整路径

从进入目标页的调用方，跟到子流程退出后第一次接手的调用方。只整理影响此次决定的信息：

| 信息 | 要解决的问题 |
|---|---|
| 用户目标与既有入口 | 现有配置组合能否完成目标？是缺功能、入口难发现，还是已有流程提前返回？ |
| 参数与状态所有者 | 谁算次数、谁读配置、谁写 `auto.model`？本层接收的是原始配置还是已处理结果？ |
| 当前观察 | 哪张画面、哪个资源键、哪一帧支持动作？模板出现是否也可能是被弹窗覆盖的背景？ |
| 动作与下一观察 | 点击是否可能切换选择、重复消费或误触下一页？如何知道动作产生了预期结果？ |
| 退出与交接 | 本函数返回后谁继续处理？成功返回可能只是交回父循环，不代表整个游戏流程结束。 |
| 证据与适用范围 | 源码 SHA、评论或截图来源，以及相关版本、语言、主题、分辨率或实例差异。 |

简单修改可写成几句推理；有多个状态时再用表格。字段未知就指出缺口，不为填满表格推测游戏行为。

将证据区分为：**源码可证**、**人类描述**、**画面/实际轨迹可证**、**待证假设**。人类描述有价值，但涉及界面布局的旧评论不自动成为当前版本事实。新的相反证据应修正旧结论。

## 比较小方案

针对同一个触发状态，先比较现有机制能否满足目标：删除覆盖值、复用已有入口、调整判断顺序或让原所有者负责。只有这些方案不能解释已观察故障时，再引入新状态、等待、重试或配置。

代码行数不是唯一标准：少一次有效确认可能更危险，增加一层没有证据的恢复也可能制造新动作。比较的是行为是否完整、动作是否必要、维护责任是否集中。

## 按流程选择历史案例

以下是带版本边界的案例索引。只读本次相关项，并在目标树重新核对源码；它们不是当前所有模式的完整规格。

### 采光连战：次数由任务层决定

- 历史锚点：上游 PR #691，审阅前 `7dbfca10`；入口 `tasks/base/script_task_scheme.py::Daily_task` → `tasks/daily/luxcavation.py::exp/thread` → `Battle.fight`。
- 源码责任：任务层分批后传递本批 `combat_count`。入口层重复读取全局配置和再次分批会把两处计算混在一起。
- 人类描述：次数面板不遮挡入口，增加收起动作没有必要。[维护者说明](https://github.com/KIYI671/AhabAssistantLimbusCompany/pull/691#issuecomment-4682043417)。该布局本轮未实测。
- 同一讨论中，作者先称纽本次数框只在外层，随后纠正为内外都能点。不要把最早解释当作事实。
- 特征搜索范围不仅由 `model` 决定，还取决于资源裁剪与 bbox；去掉 `_assets` 后缀需要同时核对模板内容，不能只改名。

### 体力换饼：先查既有入口的提前返回

- 历史锚点：PR #777 基线 `f2fcf482`；`Buy_enkephalin` → `lunacy_to_enkephalin` → `make_enkephalin_module`。
- 在这条路径里，“不换狂气”和“不要换饼”是两个不同决定。上层 `times == 0` 的提前返回会跳过后者。
- 上游最终在 `b60102c0` 统一该入口：不换狂气时只换饼，换 N 次时随后换饼；关闭了新增独立开关的 PR。[处理结论](https://github.com/KIYI671/AhabAssistantLimbusCompany/pull/777#issuecomment-4959162888)。
- 检查新增任务时，先追配置组合到实际调用，不能仅凭 UI 名称判断“没有这个功能”。

### 网络重试：一帧不能证明动作后的状态

- 历史锚点：PR #677 `8aa21f20` → 修正 PR #683 `9958fc3f`，`back_init_menu` → `retry`。
- `skip_screenshot=True` 在重试内循环中持续生效；若旧帧仍显示 connecting，即使游戏已经离开该页，循环也看不到变化。
- 最终方案移除开关，并移除调用方紧邻的重复截图，由 `retry` 刷新。[最终改动](https://github.com/KIYI671/AhabAssistantLimbusCompany/pull/683/files)。
- “刚截过图”只描述时间，不证明截图后未发生点击、异步跳页或窗口变化。

### 奖励卡：选择可能切换，退出可能是交接

- 本地源码锚点 `fb4f607f`：`Battle.fight` → `get_reward_card` → `Mirror.run`。
- 奖励卡画面需要先于结算中心点击判断；中心点击可能预选卡片，下一次选择再把它取消。[PR #750](https://github.com/KIYI671/AhabAssistantLimbusCompany/pull/750)。
- `reward_card.py` 识别饰品选择页后返回，`mirror.py` 的父循环接手；不能仅凭该返回认定奖励流程漏处理。
- `model=None` 继承 `auto.model`，而奖励卡循环会将它升级为 `normal/aggressive`；显式 `model="clam"` 可能在保留局部搜索契约，并非等于初始值就冗余。

### 商店刷新：未知经费不等于足够经费

- 历史锚点：PR #675 `51798089` → `dbf8a9ce`；`Shop._get_cost` → `buy_gifts`。
- `_get_cost()` 失败返回 `-1`。旧补丁用 `< 0 or >= 300/200` 放行刷新，并在原普通刷新之前加入另一份普通刷新分支。
- 看完整方法和返回值即可发现这两点，无需游戏反编译。[维护者讨论](https://github.com/KIYI671/AhabAssistantLimbusCompany/pull/675#discussion_r3389671460)。
- 条件同时成立不等于同一轮一定执行两次，仍要读 `continue` 和点击成功分支。

## 选择验证证据

- **调用链、默认值、分支可达性**：读目标历史树，必要时提取原函数或条件做冷验证。
- **模板能否识别某页**：复用 `replay-matching` 的生产匹配管线；一张截图不能验证点击后的游戏变化。
- **动作时序或交接**：使用已有的短录屏/连续截图及对应日志。标注动作前后画面、帧与动作顺序、实际结果；不要求用户录完整一局。
- **环境差异**：记录本次失败相关的身份信息。例如 PR #803 的 MuMu 问题，Manager 就绪不能证明所加载 DLL 与目标 Android 实例相匹配。[最终根因说明](https://github.com/KIYI671/AhabAssistantLimbusCompany/pull/803#issuecomment-5016302720)。

人工编写的 fake frames 可测试代码是否遵守一条已知轨迹，但不能用来证明该轨迹符合游戏。若动作没有对应的已知后继，保留未知，不让假环境按“截图次数”自动走到期待页面后宣称实机通过。

## 历史回看

复审先固定 base、被评版本和最终 head；已解决的评论不是最终版本的待修缺陷。读过人工答案的实验称为回溯验证。只有未见答案、冻结输入的独立试用才能作为留出案例；少量案例不能推导整体准确率。
