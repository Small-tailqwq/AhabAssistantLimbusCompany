# Agent Note: 更新引导器以协议和托管清单维护文件所有权

Status: implemented

## 问题

安装目录同时包含发行包文件、用户配置、日志、锁文件和其他运行期数据。新发行包没有包含某个文件，只能说明新版本不交付它，无法证明 updater 有权删除它。

`v1.5.0-canary.9` 使用安装目录与新包文件的差集清理；压缩包多一层 `AALC/` 时，相对路径还会失配，扩大到运行所需的 `_internal/`。仅修正压缩包布局仍不能解决用户文件的所有权问题。

在线更新首先运行安装目录中的 `AALC Updater.exe`。新包里的修复无法约束已经开始运行的旧 updater，因此文件保护和引导器能力演进需要分别处理。

## 决策

### 文件所有权与职责

[update_protocol.py](../../../../module/update/update_protocol.py) 统一协议路径、版本比较、路径校验、构建清单和兼容版本选择。[构建脚本](../../../../scripts/build.py) 声明交付内容，[应用更新模块](../../../../module/update/check_update.py) 选择本地引导器可处理的发布包，[Updater](../../../../updater.py) 负责解压、安装及本地清单持久化。

覆盖安装仅使用新包的 `managed_files.txt`；退役清理仅使用 `旧 installed_manifest - 新 managed_files`。安装目录全扫描、目录名称以及新包缺席都不是文件所有权依据。这个约束同时保护覆盖和删除；不能只在清理时排除用户路径。

首次没有已安装清单时，不具备差集清理的旧基线。安装程序写入第一份清单，后续更新才有可比较的托管集合。保留无法证明归属的历史文件，是这一选择接受的代价。当前资源整目录清理与该约束的偏差见“当前覆盖缺口”。

### 构建产物与版本标记

| 文件 | 作用 |
| --- | --- |
| 包内 `update_manifest.json` | 描述协议、引导器版本、包布局、清理模式、清单名称、清单摘要和保护路径。 |
| 包内 `managed_files.txt` | 最终分发目录中的托管文件相对路径，一行一个，以 `/` 分隔；不包含自身、`update_manifest.json` 或保护路径。 |
| Release 的 `AALC.update_manifest.json` | 构建时从包内 manifest 复制的旁置清单，让应用在下载完整包前选择兼容版本。 |
| `assets/config/installed_manifest.txt` | 上次安装写入的托管路径集合，作为下一次退役清理的旧基线。 |
| `assets/config/installed_manifest_meta.json` | 当前实现保存 `current_version`、`bootstrap_version`。 |
| `assets/config/bootstrap_version.txt` | 随托管文件安装的本地引导器版本标记。 |

构建在资源整理和裁剪完成后生成清单及其 SHA-256，避免先生成清单再改变分发内容。当前输出为 `format_version=1`、`cleanup_mode="manifest"`、`min_source_version_for_cleanup="0"`；`bootstrap_version` 默认 `2`。常规包为 `flat` 布局，`--bridge-updater` 才产生带 `AALC/` 顶层目录的 `root_dir` 布局；协议没有 `payload_root` 字段。

`bootstrap_version` 不随普通应用版本递增，仅在引导器协议能力不兼容时提升。正常 Canary 构建与发布要求见[构建指南](../../../../assets/doc/zh/build_guide.md)，历史桥接选项不用于常规发版。

### 包内清单与路径校验

`load_managed_files()` 在复制前读取清单，将 CRLF 规范为 LF 后校验 `managed_files_sha256`，随后逐条验证路径和来源文件。摘要绑定清单内容；它不是各负载文件的逐文件摘要或发布者签名。

保护路径使用大小写不敏感的完整路径或目录前缀匹配。manifest 可扩展保护集合，不能削弱 `DEFAULT_PROTECTED_PATHS`：`config.yaml`、`theme_pack_list.yaml`、`logs/`、`update_temp/`、`3rdparty/`、`theme_pack_weight/`、`__pycache__/`。新增运行期目录需要判断其所有权，并在需要保护时纳入该集合。

`validate_relative_manifest_path()` 拒绝绝对路径、盘符、UNC、`..`、冒号、空路径、根路径和受保护目标。复制来源及安装目标再经 `resolve_safe_child()` 验证解析结果仍位于各自根目录内。声明为托管的来源文件必须存在；包中未列入清单的其他内容不会通过 `copy_payload()` 安装。

清单缺失、摘要不符、非法路径、来源缺失、保护集合被削弱、无效引导器版本或包内版本标记不匹配均使安装报错。有效负载的首次迁移可以跳过退役清理；不可信负载本身不能降级为忽略错误继续复制。

### 本地清单与退役清理

`load_installed_manifest()` 校验旧路径语法，但允许旧记录包含如今受保护的路径。删除时使用新包的保护集合再次过滤，使新增保护规则能保住历史清单中的文件。

`should_allow_cleanup()` 要求旧集合非空、来源版本存在且高于 `LEGACY_DANGEROUS_VERSION`（`1.5.0-canary.9`），清理模式为 `managed_only` 或 `manifest`；提供非空 `min_source_version_for_cleanup` 时还需满足版本下限。旧集合缺失或为空时跳过退役清理。

来源版本优先读取已安装元数据的 `current_version`，再读取 `assets/config/version.txt`。清理基于来源安装版本，不能拿刚安装的新版本替代；当前读取时机的缺口见下文。

复制完成后，退役路径逐文件删除；单个 `unlink()` 失败会打印错误并继续，不阻断其余清理。随后写入新的托管清单及版本元数据。无法删除的旧文件可能残留，且不会出现在新基线中；清理不是回滚或原子安装机制。

### 应用兼容性选择与桥接边界

应用读取本地 bootstrap 标记；缺失、无效或小于 `1` 时按 `1` 处理。候选 Release 必须恰有一个匹配 `AALC_.+\.7z` 的包和一个 `AALC.update_manifest.json`，旁置清单必须显式提供有效正整数 `bootstrap_version`。`select_compatible_release()` 在引导器要求不高于本地版本的候选中选应用版本最高者，不依赖 API 返回顺序。

Stable 过滤 prerelease，Canary 使用完整 releases 列表。最新有效候选要求更高 bootstrap、但存在较旧兼容候选时，界面说明先安装兼容桥接版本。没有兼容候选时不下发其压缩包地址；当前提示行为的缺口见下文。

桥接先解决本地 updater 的替换，后续更新才由新引导器执行。桥接包需要是旧 updater 能处理的完整应用包，并携带新 updater、bootstrap 标记和协议文件；只替换一个可执行文件的增量包无法满足旧清理逻辑对完整负载的假设。`--bridge-updater` 仅改变包布局，不自动建立从任意旧 bootstrap 到新版本的兼容路径，仍需验证发布元数据与实际旧客户端能否消费。

由 `canary.9` 旧 updater 执行的桥接运行仍受旧删除逻辑控制，新协议无法保证保留其历史日志。发布或验证桥接时必须以实际旧二进制为依据；需要保留用户数据或主程序已无法启动的安装，使用备份后的手动完整包恢复，不能依赖应用内更新入口自救。

## 曾考虑的替代方案

### 扫描安装目录，删除新包没有的文件

这是托管清单替代的旧实现。扩大保留白名单仍无法列举用户未来生成的所有合法文件；包布局失配还会把正常程序文件误判为残留。旧安装清单提供明确的应用所有权，新包缺席只用于判定其中哪些路径已退役。

### 首次迁移时清理全部历史残留

首次安装新协议没有可信旧基线。猜测历史文件归属会把迁移风险集中到最缺少元数据的用户，因此选择保留无法证明归属的旧文件，先建立清单。

### 只在新包内修复 updater

新包里的 updater 替换不能改变正在运行的旧 updater。协议把旧版本过渡与后续受控更新分开；不把同一次旧 updater 运行视为已经受新协议保护，也不引入自动双阶段网络接管。

### 长期保留带顶层目录的默认包布局

`root_dir` 用于兼容旧 updater，常规构建采用 `flat`，减少应用根的层级歧义。保留显式历史构建选项满足桥接需要，普通版本不因此继续使用旧布局。

## 后果

托管清单使用户文件保护不再依赖“安装目录只能放程序文件”的假设，代价是维护本地基线、保护集合和发布协议。新旧清单、旁置 manifest 与包内 bootstrap 标记都必须保持一致；不能通过手改旁置文件绕过兼容性选择。

### 当前覆盖缺口

以下是当前实现与所有权或协议约束之间的缺口，不是扩大 updater 权限的依据：

- `apply_update_from_extracted_payload()` 在解压目录没有 `changes.json` 时仍整体删除 `assets/images`，独立于旧托管清单和退役清理资格。因此首次迁移当前只能确认跳过清单差集删除，尚未实现全流程零删除；新增清理逻辑仍须遵守文件所有权约束。
- `discover_payload_root()` 仍通过是否存在 `AALC/` 子目录探测应用根；`validate_manifest_metadata()` 没有校验 `format_version` 或 `package_layout`。构建虽写出这些字段，安装器尚未落实按声明拒绝未知格式或布局失配的保护。
- 本地旧清单没有摘要校验；元数据只保存应用和 bootstrap 版本。`should_allow_cleanup()` 在复制之后调用，无有效旧元数据时可能读取已覆盖的 `version.txt`；无法解析的版本还会使清理判断抛异常，尚未落实“不可信来源版本只覆盖、不删除”的完整行为。
- 复制逐文件进行，重试最多 `5` 次，没有事务回滚。目标路径在各次复制时校验，后续文件失败前可能已覆盖前面的文件；更新失败重开已有主程序不等于恢复旧安装。
- 应用的 `UpdateThread.run()` 当前把“没有兼容包”的 `RuntimeError` 记为当前已是最新并发出 `SUCCESS`，尚未提供协议设计要求的明确手动恢复提示。

### 必要验证与现有覆盖

[test_update_protocol.py](../../../../tests/test_update_protocol.py) 包含路径与保护集合、清单生成、bootstrap 读取、候选选择、首次迁移、托管差集清理和安装失败处理等检查。涉及这些机制的变更应保留以下行为验证，按改动选择相关现有检查：

- 首次没有旧清单时保留日志、锁文件和未知用户文件，写入新的本地基线；后续只删除旧清单中已退役的文件。
- 旧清单含如今受保护的路径时保留该文件；包不能放宽默认保护集合或把用户配置声明为托管。
- 清单摘要不符、绝对路径、盘符、UNC、`..`、越出来源或安装根以及来源缺失时拒绝安装，不发生清理或用户文件覆盖。
- 来源为危险版本、低于清理下限、无法确定或无法解析时不执行退役删除；来源版本须在覆盖前确定。
- 负载布局与格式声明一致；单一压缩包、旁置清单、包内 bootstrap 标记与本地能力检查相符。
- 旧 updater 到桥接版本、桥接版本到协议版本分别验证；直接调用当前 `Updater` 的模拟测试不能代替旧二进制运行，也不能覆盖真实 Windows 文件占用和应用启动。

现有安装测试没有覆盖上述资源整目录删除、未知 `format_version`/布局声明拒绝或缺少旧元数据时的版本读取顺序。这些缺口保留为后续更新器工作需要处理的边界，不能由文档迁移宣称已经通过。
