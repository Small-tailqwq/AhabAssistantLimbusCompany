# 游戏流程核对与历史契约回放

自动化变更需要同时核对进入界面、执行动作、退出后的接手者。代码调用关系和真实游戏画面承担不同的验证职责。

## 阅读顺序

1. 确定任务层参数的所有者，再读入口、动作与战斗函数。例如采光次数由任务层分批，入口与战斗层需要使用同一批次数。
2. 查看完整方法、直接调用方和返回值。奖励卡函数返回可能表示由镜牢父循环接手；返回值不是完整流程结束的统一标记。
3. 核对省略参数后的有效值。固定默认阈值可以与显式传参等价；`model=None` 会读取可变的 `auto.model`，不能直接当作固定模式。
4. 页面切换后的判断使用新截图。重试循环刷新截图，避免一直对同一张 connecting 画面作判断。
5. 动作时序和模板识别依赖对应版本的截图、日志或连续画面；没有后继画面时保留未知。

任务失败需要沿调用方传播。日常子任务返回 `False` 时，调度停止后续任务；程序退出只接受整数退出码 `0`。模板匹配、任务返回值和游戏实际进度应分别核对。

## 离线历史回放工具

```powershell
uv run python .\debug_tools\verify_historical_flow_contracts.py
```

该脚本从本地 Git 读取固定历史提交，提取 Python 函数或条件执行，不导入 AALC 运行时。它用于复查已保存的历史契约：

| 案例 | 核对内容 |
| --- | --- |
| 网络重试 | 复用旧截图与循环内刷新截图的差异 |
| 商店刷新 | 识别失败值及重复刷新条件的可达性 |
| 采光阈值 | 省略参数后的固定默认阈值 |
| 奖励卡模式 | 省略模式继承可变状态，显式模式保持局部契约 |

工具输出描述所提取的历史源码，不作为当前待修清单，也不测量游戏识别率、动作时序或设备可靠性。克隆历史不完整时，需要先取得脚本引用的提交。

## 验证范围

- 源码及冷执行：默认值、参数传递、返回值与分支可达性。
- 模板重放：使用仓库生产匹配管线验证特定截图中的模板与坐标。
- 流程交接：使用已有连续画面或日志，核对动作前后界面及接手者。
- 设备故障：结合模拟器版本、实例、截图与输入方式，区分启动状态和实际连接状态。

用 fake frames 可以检查代码是否遵守已知序列；序列本身是否符合游戏，需要独立画面证据。专项约定见 [游戏流程证据](../.agents/skills/aalc-automation-practices/references/game-flow-evidence.md)。
